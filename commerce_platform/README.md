# Commerce Analytics Platform

**[Открыть платформу](https://manhalrr.github.io/Rafif/commerce_platform/)** · [Все проекты Рафиф](https://manhalrr.github.io/Rafif/) · [Архив исходников](https://manhalrr.github.io/Rafif/downloads/Commerce_Analytics_Platform.zip)

Сквозной проект аналитики интернет-магазина: **1 067 371 исходная строка → проверка качества → SQLite-хранилище → SQL-витрины → интерактивный дашборд → рекомендации и прогноз**.

В источнике два года реальных исторических операций одного британского магазина. Это открытые данные UCI, а не сведения работодателей. Показатели не заявляются коммерческими достижениями Рафиф или эффектом внедрённой системы.

## Что посмотреть за две минуты

1. **Обзор бизнеса:** 24 месяца, 43 географических значения, фильтры страны и периода, экспорт CSV. Выберите Germany, январь–март 2011: оборот после отмен **£39 590,69**, **82 заказа**. На карточках суммы округляются до фунта, экспорт хранит точные целые пенсы.
2. **Ассортимент:** 4 930 товарных/служебных кодов, ABC по положительным продажам, поиск, сортировка, пагинация и экспорт выборки. Класс A — 1 016 кодов. ABC не заменяет анализ маржи или наличия.
3. **Удержание:** 24 когорты, M0–M11, взвешенные показатели только по зрелым окнам. Будущие периоды пустые, а не нулевые.
4. **Прогноз:** три базовые стратегии; шесть последовательно проверенных месяцев. Seasonal lag12 даёт WAPE **6,04%** на этих шагах, но выбирается на них же — это не независимая оценка выбранной модели.
5. **Качество:** доказанное межлистовое перекрытие **22 523 строк**, явное правило владения периодами, SHA-256, контроль знаменателей, дублей, финансовых сумм и SQL/pandas.
6. **Архитектура:** источник, факт/измерения, SQL-марты, воспроизведение и ссылки на исходники.

## Почему проект не ограничивается красивым дашбордом

В UCI Online Retail II листы перекрываются 1–9 декабря 2010. Простое объединение завысило бы оборот. Конвейер проверяет равенство мультимножеств пересекающихся строк, выбирает первый лист до 01.12.2010 и второй — с этой даты. Неоднозначные точные повторы внутри выбранных периодов сохраняются, а чувствительность к их удалению оценивается отдельно.

Деньги округляются **Decimal, half-even, на уровне строки** и далее хранятся целыми пенсами. Количество заказов имеет определённый ключ. Результаты SQL независимо сверены с pandas. Прогноз каждого шага видит только предшествующие месяцы. Опубликованный интерфейс получает готовые агрегаты; строки отдельных клиентов и локальная база в веб-пакет не включены.

## Воспроизведение

Требуется Python **3.11+**. Проверенное окружение зафиксировано в протоколах; зависимости публичные и указаны в `requirements.txt`. SQLite входит в Python. Переносимость SQL на другую СУБД не заявляется.

```sh
git clone https://github.com/ManhalRR/Rafif.git
cd Rafif/commerce_platform
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python run.py
python forecast.py
python verify_package.py
```

Первый полный запуск загружает официальный архив UCI (~43,5 MB), сверяет SHA-256 и сохраняет локальный источник в `data/`. Пересборка требует оперативной памяти для двух листов и расчётов; время зависит от компьютера. Файлы источник/кэш/SQLite не коммитятся.

Если исходник уже скачан:

```sh
python run.py --input "/path/to/online_retail_II.xlsx"
```

Запуск интерфейса из корня репозитория:

```sh
cd ..
python -m http.server 8000
# http://localhost:8000/commerce_platform/
```

При распаковке отдельного архива также запускайте HTTP-сервер из папки, содержащей `commerce_platform/`. Сам дашборд работает без внешних библиотек, API-ключей и серверной базы. Навигация на всё портфолио и скачивание полного архива ведут на опубликованный сайт. `file://` не подходит для загрузки JSON через fetch.

## Проверки без загрузки большого XLSX

```sh
python run.py --tests-only
python forecast.py --tests-only
python verify_package.py
```

- Ядро: **31 сверка на настоящих данных + 11 тестов граничных случаев — 42 проверки**. Включены контроль первичного источника, перекрытия листов, ссылочной целостности, целочисленных сумм, месячных/страновых/товарных итогов, заказов и будущих когортных окон. Повторный полный запуск дал побайтно одинаковые пять итоговых CSV; протокол — `results/reexecution_validation.json`.
- Прогноз: **8 тестов**, включая отсутствие утечки, корректность lag12, знаменатель WAPE при отрицательных/нулевых фактах и исключение неполного месяца.
- `verify_package.py`: контракт опубликованных JSON/CSV, сверка итогов, заполненность месяцев, ссылки исходников и отсутствие сырых клиентских выгрузок.
- Проверка браузера хранится отдельным датированным протоколом; запуск Python не выдаётся за ручной просмотр интерфейса.

Счётчики отражают реально выполненные проверки, а не гарантию отсутствия любых ошибок. [Протокол ядра](results/validation.json), [дизайн прогнозирования](FORECAST.md), [помесячная проверка](results/forecast_backtest.csv).

## Дизайн прогнозирования

Сравниваются последний месяц, среднее трёх месяцев и соответствующий месяц прошлого года. Проверка — июнь–ноябрь 2011, на каждом шаге используется только более ранняя история. Критерии — MAE и WAPE. Seasonal12 выбран по этим же шести точкам: его качество после выбора не оценено на отдельном тестовом периоде.

Ориентир на декабрь 2011 — **£748 957,02**. Это значение сезонной стратегии, не известный итог декабря и не обещание будущей точности. Достоверный прогнозный интервал на шести ошибках не заявляется. Для внедрения потребуются больше истории, календарь акций, реальные изменения бизнеса и новый независимый период оценки.

## Как защищать решение на собеседовании

- **Почему два листа нельзя просто объединить?** В них одинаковый диапазон декабря 2010; проверка мультимножеств и правило владения устраняют двойной учёт.
- **Почему не удалить все одинаковые строки?** Без уникального ID позиции нельзя отличить ошибку от повторной позиции. Межлистовое перекрытие и точные повторы — разные проблемы.
- **Почему число заказов нельзя складывать по товарам?** Один заказ может содержать несколько кодов. В разных витринах используются разные единицы анализа.
- **Почему M1 не среднее процентов?** У когорт разный размер; корректный общий показатель — сумма вернувшихся / сумма исходных клиентов только зрелых когорт.
- **Почему не назвать продажи прибылью?** Для прибыли нужны затраты; для причинного эффекта рекомендации нужен подходящий эксперимент.
- **Почему простая модель прогноза?** Она даёт прозрачный ориентир. Сначала проверяется, превосходит ли сложная модель простую стратегию на новых данных.
