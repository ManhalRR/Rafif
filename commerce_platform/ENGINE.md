# Расчётное ядро Commerce Analytics Platform

Полноценный воспроизводимый конвейер на **реальных UCI Online Retail II**: источник → проверка происхождения и перекрытия → нормализация → измерения/факт SQLite → SQL-витрины → независимые сверки → публичные агрегаты.

## Запуск

```sh
python -m pip install -r requirements.txt
python run.py
```

Первый запуск скачивает [официальный ZIP UCI](https://archive.ics.uci.edu/static/public/502/online%2Bretail%2Bii.zip). Для своего локального экземпляра **того же** исходника:

```sh
python run.py --input "/absolute/path/online_retail_II.xlsx"
python run.py --tests-only
```

Необходим Python 3.11+; проверенная среда — Python 3.12, pandas 3.0.1, NumPy 2.3.5, openpyxl 3.1.5, SQLite из стандартной библиотеки. Не требуются Excel, Power BI, внешняя БД или приватные пакеты.

Отсутствующий явно указанный файл — ошибка. Повреждённый ZIP, другой SHA, иной набор листов/колонок, неожиданное перекрытие или провал сверки останавливает выполнение с ненулевым кодом. Скрипт не подменяет данные синтетическими.

## Зафиксированный источник

Chen, D. (2012). [Online Retail II](https://doi.org/10.24432/C5CG6D). UCI Machine Learning Repository. [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). В проекте данные преобразованы, очищены и агрегированы.

| Артефакт | SHA-256 |
|---|---|
| Официальный ZIP, 45 622 418 байт | `572e36277c2390fbfde10664750731e0a86f55e33470d91919085f0408e67bfb` |
| XLSX, 45 622 278 байт | `bcbe73b35f5b7babf197fb0cb983a11f5d9ff929078d4aa53d171b1f2df2e980` |

Эти хеши зафиксированы после загрузки по официальному URL. Они обеспечивают воспроизведение на том же файле; отдельная цифровая подпись издателя не заявляется.

### Существенная аномалия: пересечение годовых листов

| Лист | Строк | Начало | Конец |
|---|---:|---|---|
| Year 2009-2010 | 525 461 | 01.12.2009 07:45 | 09.12.2010 20:01 |
| Year 2010-2011 | 541 910 | 01.12.2010 08:26 | 09.12.2011 12:50 |

На обоих листах присутствуют **22 523 строки / 1 088 invoice за 1–9 декабря 2010**. Проверяется равенство мультимножеств хешей всех 8 исходных полей, с сохранением кратности повторов. Простое объединение листов удвоило бы эти операции и исказило декабрь 2010 — в том числе сезонную базу для прогноза.

Явное правило владения: первый лист до 1 декабря 2010, второй начиная с этой даты. **22 523 строки первого листа исключаются как перекрытие. Остаётся 1 044 848 строк до проверок качества.** Если содержимое перекрытия перестанет совпадать, процесс завершится ошибкой, а не молча выберет произвольный вариант.

Это не обычное удаление одинаковых строк. Внутри выбранных периодов точные повторы сохраняются: уникального идентификатора товарной позиции нет. Отдельно измеряется чувствительность net к удалению дополнительных совпадающих строк. Происхождение каждого принятого факта сохраняется ключом `sheet:ExcelRow`.

## Результаты исполненного расчёта

Полный прогон: **31 сверка + 11 граничных тестов = 42 проверки без ошибок**. Независимое ревью отдельного исполнителя также пересчитало все 24 месячных агрегата из исходных листов через Decimal и сверило их с SQLite/CSV.

| Показатель | Значение |
|---|---:|
| Строк после владения периодами | 1 044 848 |
| Принятых строк после качества, весь доступный период | 1 038 818 |
| Принятых строк в отчётных 24 месяцах | 1 013 346 |
| Положительный оборот | £19 894 931,22 |
| Сумма отмен | £1 260 552,56 |
| Оборот после отмен | £18 634 378,66 |
| Заказы с продажами | 39 258 |
| Уникальные известные покупатели | 5 850 |
| StockCode с операциями | 4 930 |
| Страны / страна × месяц | 43 / 573 |
| Когортные ячейки M0–M11 | 288 |

После разрешения перекрытия исключены 6 029 строк неположительной цены: 6 024 нулевых и 5 отрицательных. Дополнительно исключена **одна строка Manual с C-префиксом, положительным количеством и суммой £373,57**: её знак противоречит принятому правилу отмен. Строка не переворачивается в отмену по предположению. Необходима бизнес-классификация такой ручной операции; выбранная политика и её денежный охват открыты.

11 812 дополнительных точных повторов остаются в выбранных периодах. Удаление этих повторов снизило бы отчётный net на **£53 261,47**. Это отдельная чувствительность к неопределённости строк, а не межлистовое дублирование: перекрытие уже исключено до неё.

Аудит Invoice не обнаружил номеров, охватывающих несколько стран или месяцев: plain и composite дают одинаковые **39 258** заказов. Составной ключ сохраняется как явное устойчивое определение и проверяется тестами на искусственных коллизиях.

Повторная полная обработка XLSX дала побайтно одинаковые monthly, country_month, products, cohorts и quality_monthly CSV. Протокол — `results/reexecution_validation.json`; изменения граничного теста между запусками в нём раскрыты. Он фиксирует реально выполненное сравнение и не подменяется новым успешным результатом при каждом запуске.

## Правила нормализации

Причины исключения применяются последовательно: невалидная дата → нулевое/нецелое/невалидное количество → неположительная/невалидная цена → отсутствующий invoice → несовместимый знак и C-префикс. У каждой строки только одна причина. Перекрытие разрешается до этих правил.

Количество должно быть ненулевым целым числом. Цена — положительным конечным числом. Префикс C означает отмену и требует отрицательного количества; отрицательная строка без C исключается. Пропуск Customer ID не исключает продажу. Пустая страна и StockCode получают явные технические значения, а не теряются при GROUP BY.

Сумма строки считается через Decimal, округляется half-even до пенса. SQL суммирует INTEGER. Округление выполняется на сумму строки, не сначала на цену единицы. Результаты отражают принятую аналитическую конвенцию, а не воссозданный бухгалтерский регистр.

Заказы определяются составным ключом `JSON([Invoice, Country, month])`. Это защищает от повторного использования номера в другой стране/месяце. JSON-кодирование предотвращает коллизии разделителей внутри текста. Аудит простого Invoice публикуется отдельно. Число заказов по товарам нельзя суммировать: один заказ содержит несколько кодов.

## Модель и SQL

`sql/00_schema.sql` определяет три измерения и факт с внешними ключами. Факт содержит только принятые строки; время и Customer ID остаются локально. Индексы — дата/страна, продукт и клиент/дата.

| SQL | Витрина | Применяемые конструкции |
|---|---|---|
| `10_monthly.sql` | Месячные суммы и заказы | JOIN, условные суммы, COUNT DISTINCT |
| `20_country_month.sql` | Страна × месяц | JOIN измерений, составная группировка |
| `30_products.sql` | StockCode, оборот, количество, ABC | CTE, оконные суммы, детерминированное ранжирование |
| `40_cohorts.sql` | Когорты × возраст M0–M11 | Несколько CTE, recursive age grid, CROSS JOIN, LEFT JOIN, явный NULL будущего |
| `50_quality_monthly.sql` | Покрытие ID и строки | Условные счётчики и GROUP BY |

SQL-результаты сохраняются как `mart_*` в SQLite и CSV в `results/`. `dashboard.json` следует контракту PROJECT_INTERFACE.md. Клиентские строки, исходная книга и SQLite не включаются в публичные результаты.

## Проверка корректности

Для каждого полного запуска реально выполняются:

- SHA-256, число строк, схема листов и равенство перекрытия с учётом кратности;
- уникальность происхождения строк, foreign_key_check и integrity_check SQLite;
- покрытие ровно 24 полных месяцев;
- независимые pandas/SQL-сверки **каждого месяца**, стран/месяцев и продуктов;
- независимый пересчёт всех 288 когортных ячеек, в том числе наблюдаемых нулей и будущих NULL;
- денежная идентичность gross − cancellations = net и сверки всех витрин;
- уникальность страны/месяца для составного заказа и аддитивность orders;
- согласованность клиентской базы, M0 и допустимого диапазона retention;
- сортировка/доли ABC, сверки качества и пропусков;
- 11 граничных fixture-тестов: ошибочные строки, отмена без продаж в месяце, неизвестный клиент, повторы, границы периода, будущие когорты, округление, равные суммы ABC и неопределённая доля при отсутствии положительного оборота.

Fixture-данные используются только для проверки алгоритма. Аналитические результаты получаются из реального UCI-файла. `results/validation.json` содержит фактический протокол, UTC-время, версии, хеш источника и локальной БД. Ручная проверка интерфейса данным скриптом не объявляется.

## Идемпотентность и публикация

Каждый полный запуск строит новую `data/warehouse.build.sqlite`, выполняет сверки и лишь после успеха заменяет `data/warehouse.sqlite`. Факты не дописываются в существующую базу, поэтому повторный запуск не удваивает продажи. Публичные агрегаты перезаписываются детерминированно; служебная дата проверки меняется. При ошибке сборки остаётся предыдущая успешная БД и прежние публичные результаты.

`data/` — локальный кэш: ZIP, XLSX, warehouse и вспомогательные исследовательские файлы. Его содержимое не публикуется. В `results/` нет фактических Customer ID и строк отдельных заказов. Наблюдения отдельных клиентов существуют только внутри локального расчёта.

Фронтенд, прогнозирование и публикация — отдельные модули. `run.py` не меняет forecast-файлы, не выполняет deployment и не делает утверждений о производственной эксплуатации.

## Ограничения интерпретации

- Один исторический магазин с розничными и, возможно, оптовыми покупателями. Это не репрезентативная выборка всего рынка.
- Два года позволяют наблюдать сезонность, но слабо защищают от изменения бизнеса и единичных крупных заказов. Прогноз требует внешнего мониторинга.
- Первая покупка наблюдаемая, а не доказанное привлечение клиента. История до декабря 2009 неизвестна.
- Отмены не связаны надёжно с исходной продажей. Средний чек и денежные отношения зависят от выбранной конвенции.
- Нестандартные/сервисные коды включены. ABC описывает оборот, не прибыльность и не оптимальный ассортимент.
- Нет себестоимости, складских остатков и коммуникаций. Нельзя заявлять маржу, ROI, stockout, причинный рост продаж или результат внедрения.
- Данные и расчёты — публичный аналитический кейс, не подтверждение коммерческих результатов у работодателя.
