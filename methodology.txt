РАФИФ АЛШАУИ - ПОРТФОЛИО АНАЛИТИКА ДАННЫХ
Версия от 27 октября 2026 года.

СОДЕРЖАНИЕ
Два законченных воспроизводимых аналитических кейса: продажи и когортный
анализ на открытых данных UCI; модель A/B-эксперимента на синтетических данных.
Включены постановка задачи, обработка данных, SQL, статистика, визуализации
и интерпретация. Реализация: Python, SQLite, Excel и автономный HTML-дашборд.
Название и внутренние данные работодателя в материалах не используются.

БЫСТРЫЙ ПРОСМОТР
Откройте index.html в современном браузере. Интернет для дашборда не требуется.
В нём работают выбор страны, начального и конечного месяца и переключение
между проектами. Таблица когорт имеет собственный фиксированный период,
который явно указан и не меняется при фильтрации продаж.
Начните с reports/Rafif_Project_Overview.pdf: одна страница с бизнес-задачами,
методами, результатами и выводами.
Подробный отчёт: reports/Rafif_Analytics_Portfolio.pdf (3 страницы).

EXCEL И РАБОЧИЕ СКРИНШОТЫ
Откройте excel/Retail_Analytics.xlsx в Excel. На листе «Продажи» выберите
страну в жёлтой ячейке: формулы SUMIFS пересчитают таблицу и диаграмму.
На листе «Когорты» показаны M0–M5, условное форматирование и взвешенное M1.
Лист «Данные» содержит агрегаты из SQL, источник и правила расчёта.
Диаграммы являются объектами Excel и связаны с ячейками, а не картинками.
Книга проверена в Microsoft Excel: все страны и Германия, формулы и графики.
screenshots/ содержит реальные снимки открытой книги и SQL-файла в редакторе.
Для пересборки книги нужен Node.js и пакет @oai/artifact-tool:
node build_workbook.mjs. Готовый XLSX не требует этого пакета для просмотра.

ВОСПРОИЗВЕДЕНИЕ
Требуется Python 3.11+ (pandas 3.0.1 не поддерживает Python 3.10).
1. Установить зависимости расчётов: python -m pip install -r requirements-core.txt
2. Рассчитать метрики: python analyze.py
3. Для повторной генерации PDF/HTML установить полный набор:
   python -m pip install -r requirements.txt
   python present.py
4. Сформировать обзор кейсов: python brief.py
Для генерации PDF present.py использует Arial из C:/Windows/Fonts.
Для другой ОС замените пути на шрифты с поддержкой кириллицы.
Если data/Online Retail.xlsx отсутствует, analyze.py загрузит официальный
архив UCI. Это единственный сетевой шаг расчётного конвейера. SHA-256 исходника
проверяется до расчётов; при изменении источника скрипт останавливается.
SQLite-база пересоздаётся из исходных данных и не включена в ZIP для экономии места.

POWER BI
Готовый редактируемый проект: powerbi/Retail_Analytics.pbip.
Пересборка снимков после расчётов: python build_powerbi.py.
Проверка структуры: python -m pip install -r requirements-powerbi.txt,
затем python validate_powerbi.py. При первом запуске проверка загружает
официальные JSON-схемы Microsoft с GitHub; следующие запуски используют кэш.
44 проверки структуры и данных не заменяют запуск Power BI Desktop:
отрисовка страниц и выполнение DAX в Desktop пока не проверены, PBIX не включён.
Подробная инструкция и ограничения: powerbi/README.txt.

ПРОЕКТ 01. ПРОДАЖИ И КОГОРТЫ
Бизнес-вопросы: как меняется оборот, где сосредоточены продажи, сколько
клиентов повторно покупают в следующий месяц, какие ограничения имеют данные?
Источник: Chen, D. (2015). Online Retail [Dataset]. UCI Machine Learning Repository.
DOI: https://doi.org/10.24432/C5BW33
Страница: https://archive.ics.uci.edu/dataset/352/online%2Bretail
Лицензия: Creative Commons Attribution 4.0 International.
https://creativecommons.org/licenses/by/4.0/
Трансформации: нормализация, фильтрация, денежные агрегации, когортные таблицы,
визуализация. Исходные данные содержат исторические операции 2010-2011 годов.

Правила расчёта:
- Отчётный период продаж: 2011-01-01 включительно - 2011-12-01 исключительно.
  Декабрь 2011 неполный. Декабрь 2010 используется как история для когорт.
- Продажа: Quantity > 0, UnitPrice > 0, InvoiceNo не начинается с C.
- Отмена: Quantity < 0, UnitPrice > 0, InvoiceNo начинается с C.
- Некорректные даты и остальные сочетания исключаются; количество исключений
  сохраняется в results/retail_summary.json.
- Сумма строки округляется один раз до пенса: round(Quantity * UnitPrice * 100).
  Округление NumPy соответствует round-half-to-even. Это аналитическое правило,
  а не утверждение о правилах бухгалтерского учёта исходной компании.
- Оборот после отмен = сумма положительных продаж - абсолютная сумма отмен.
  Это не прибыль; НДС, себестоимость, логистика и маркетинговые затраты неизвестны.
- Стоимостное отношение отмен к продажам не равно доле возвращённых заказов:
  отмена может относиться к покупке из другого периода, прямого сопоставления нет.
- Точные повторы сохранены: в наборе нет уникального ID строки, поэтому одинаковые
  строки нельзя автоматически признать ошибками. Посчитана чувствительность к удалению.
- Неизвестный CustomerID не исключает строку из денежных метрик. Но такие строки
  не участвуют в когортном анализе.
- Когорта = месяц первой наблюдаемой положительной покупки; это не гарантированно
  первый заказ клиента за всю историю магазина. Есть левое усечение истории.
- M1 = доля клиентов когорты с положительной покупкой в следующем календарном месяце.
  Неполные будущие окна представлены NULL, а не нулём. Взвешенное M1 считается
  для январских-октябрьских когорт, без декабрьской стартовой когорты.
- В исходных строках могут присутствовать сервисные начисления и корректировки.
  Отчёт анализирует стоимость принятых строк, а не только физические товары.

ПРОЕКТ 02. A/B-ТЕСТ КОНВЕРСИИ
Все данные синтетические, генератор включён в analyze.py.
Протокол фиксирован до генерации: seed 20261027, 24 000 участников, случайное
назначение 1:1, конверсия за 7 дней, двусторонний alpha=0.05, один итоговый анализ.
Назначения моделируются 1-28 августа 2026, срез - 5 сентября, все окна завершены.
В генераторе вероятность покупки зависит от устройства; у B задан прирост 1.5 п.п.
Это известная конструкция симуляции, а не эмпирический бизнес-эффект.
ITT-знаменатель: все назначенные пользователи. Один пользователь - одна строка.
Основной тест: z-test разницы долей с объединённой оценкой дисперсии при H0.
95% интервал разницы: Newcombe на основе Wilson для двух независимых долей.
SRM: chi-square с 1 степенью свободы, ожидаемое соотношение 1:1, порог 0.01.
Незначимый SRM не гарантирует отсутствия всех ошибок рандомизации или трекинга.
Выручка на пользователя - дополнительная метрика с нормальным приближением CI;
не основание для отдельного подтверждающего вывода. Повторных просмотров p-value
и подбора seed после получения результатов нет. Реальное внедрение не моделируется.

ПРОВЕРКИ
Суммы SQL сверены с pandas; когортное M1 - с независимыми пересечениями множеств.
Проверяются размер источника, сохранение денежных итогов, корректность периодов,
диапазон удержания, NULL для будущих месяцев, уникальность участников и полнота
окна эксперимента. Итог и число пройденных проверок: results/validation.json.
